## 用户输入

```text
$ARGUMENTS
```

在继续之前，你**必须**考虑用户输入（如果不为空）。

## 目标

在实现之前，识别三个核心工件（`spec.md`、`plan.md`、`tasks.md`）之间的不一致、重复、歧义和未充分指定的项目。此命令必须仅在 `/speckit.tasks` 成功生成完整的 `tasks.md` 后运行。

## 操作约束

**严格只读**：**不要**修改任何文件。输出结构化分析报告。提供可选的补救计划（用户必须在任何后续编辑命令被手动调用前明确批准）。

**宪法权威**：项目宪法（`/memory/constitution.md`）在此分析范围内**不可协商**。宪法冲突自动为关键级别，需要调整规格说明、计划或任务——而非稀释、重新解释或静默忽略原则。如果原则本身需要更改，必须在 `/speckit.analyze` 之外通过单独的、明确的宪法更新来完成。

## 执行步骤

### 1. 初始化分析上下文

从仓库根目录运行 `{SCRIPT}` 一次，并解析 JSON 以获取 FEATURE_DIR 和 AVAILABLE_DOCS。推导绝对路径：

- SPEC = FEATURE_DIR/spec.md
- PLAN = FEATURE_DIR/plan.md
- TASKS = FEATURE_DIR/tasks.md

如果任何必需文件缺失，则中止并显示错误消息（指示用户运行缺失的前置条件命令）。
对于参数中的单引号，如"I'm Groot"，使用转义语法：例如 'I'\''m Groot'（或尽可能使用双引号："I'm Groot"）。

### 2. 加载工件（渐进式披露）

仅从每个工件加载最少必要的上下文：

**从 spec.md：**

- 概述/上下文
- 功能需求
- 成功标准（可度量结果——例如性能、安全、可用性、用户成功、业务影响）
- 用户故事
- 边界情况（如果存在）

**从 plan.md：**

- 架构/技术栈选择
- 数据模型引用
- 阶段
- 技术约束

**从 tasks.md：**

- 任务 ID
- 描述
- 阶段分组
- 并行标记 [P]
- 引用的文件路径

**从宪法：**

- 加载 `/memory/constitution.md` 以进行原则验证

### 3. 构建语义模型

创建内部表示（不在输出中包含原始工件）：

- **需求清单**：对于每个功能需求（FR-###）和成功标准（SC-###），记录一个稳定键。存在时使用显式的 FR-/SC- 标识符作为主键，并可选地推导一个命令式短语别名以提高可读性（例如"用户可以上传文件" → `user-can-upload-file`）。仅包含需要可构建工作的成功标准项（例如负载测试基础设施、安全审计工具），排除发布后的结果指标和业务 KPI（例如"减少 50% 的支持工单"）。
- **用户故事/操作清单**：具有验收标准的离散用户操作
- **任务覆盖映射**：将每个任务映射到一个或多个需求或故事（通过关键词推断/显式引用模式如 ID 或关键短语）
- **宪法规则集**：提取原则名称和 MUST/SHOULD 规范性陈述

### 4. 检测遍历（令牌高效分析）

专注于高信号发现。限制总共 50 个发现；在溢出摘要中聚合剩余部分。

#### A. 重复检测

- 识别近似重复的需求
- 标记较低质量的措辞以进行合并

#### B. 歧义检测

- 标记缺少可度量标准的模糊形容词（快速、可扩展、安全、直观、强大）
- 标记未解决的占位符（TODO、TKTK、???、`<placeholder>` 等）

#### C. 未充分指定

- 具有动词但缺少对象或可度量结果的需求
- 缺少验收标准对齐的用户故事
- 引用规格说明/计划中未定义的文件或组件的任务

#### D. 宪法对齐

- 与 MUST 原则冲突的任何需求或计划元素
- 宪法中缺失的强制部分或质量门控

#### E. 覆盖范围差距

- 零关联任务的需求
- 无映射需求/故事的任务
- 需要可构建工作的成功标准（性能、安全、可用性）未反映在任务中

#### F. 不一致

- 术语漂移（相同概念在不同文件中命名不同）
- 计划中引用但规格说明中缺失的数据实体（反之亦然）
- 任务排序矛盾（例如集成任务在基础设置任务之前，且无依赖注释）
- 冲突的需求（例如一个要求 Next.js，而另一个指定 Vue）

### 5. 严重性分配

使用此启发式对发现进行优先级排序：

- **关键**：违反宪法 MUST、缺少核心规格说明工件、或零覆盖范围的需求阻碍基线功能
- **高**：重复或冲突的需求、模糊的安全/性能属性、不可测试的验收标准
- **中**：术语漂移、缺失的非功能任务覆盖范围、未充分指定的边界情况
- **低**：风格/措辞改进、不影响执行顺序的次要冗余

### 6. 生成紧凑分析报告

输出 Markdown 报告（无文件写入），结构如下：

## 规格说明分析报告

| ID | 类别 | 严重性 | 位置 | 摘要 | 建议 |
|----|----------|----------|-------------|---------|----------------|
| A1 | 重复 | 高 | spec.md:L120-134 | 两个相似的需求 ... | 合并措辞；保留更清晰的版本 |

（每个发现添加一行；生成以类别首字母为前缀的稳定 ID。）

**覆盖范围摘要表：**

| 需求键 | 有任务？ | 任务 ID | 备注 |
|-----------------|-----------|----------|-------|

**宪法对齐问题：**（如果有）

**未映射的任务：**（如果有）

**指标：**

- 总需求数
- 总任务数
- 覆盖率 %（具有 >=1 个任务的需求）
- 歧义数量
- 重复数量
- 关键问题数量

### 7. 提供后续操作

在报告末尾，输出简洁的后续操作块：

- 如果存在关键问题：建议在 `/speckit.implement` 之前解决
- 如果仅有低/中级别问题：用户可以继续，但提供改进建议
- 提供明确的命令建议：例如"运行 /speckit.specify 进行细化"、"运行 /speckit.plan 调整架构"、"手动编辑 tasks.md 为 'performance-metrics' 添加覆盖范围"

### 8. 提供补救方案

询问用户："你是否希望我为排名前 N 的问题建议具体的补救编辑？"（不要自动应用。）

## 操作原则

### 上下文效率

- **最小高信号令牌**：专注于可操作的发现，而非详尽的文档
- **渐进式披露**：增量加载工件；不要将所有内容一次性转储到分析中
- **令牌高效输出**：将发现表限制为 50 行；汇总溢出部分
- **确定性结果**：未做更改时重新运行应产生一致的 ID 和计数

### 分析指南

- **永远不要修改文件**（这是只读分析）
- **永远不要虚构缺失的部分**（如果缺失，准确报告）
- **优先处理宪法违规**（这些始终为关键级别）
- **使用示例而非详尽规则**（引用具体实例，而非通用模式）
- **优雅地报告零问题**（输出带有覆盖范围统计的成功报告）
