## 用户输入

```text
$ARGUMENTS
```

在继续之前，你**必须**考虑用户输入（如果不为空）。

## 概述

目标：通过提出澄清问题并将答案直接记录在规格说明文件中，检测并减少活跃功能规格说明中的歧义或缺失决策点。

注意：此澄清工作流应在调用 `/speckit.plan` 之前运行（并完成）。如果用户明确声称他们跳过澄清（例如探索性尖峰），你可能继续，但必须警告下游返工风险增加。

执行步骤：

1. 从仓库根目录**一次**运行 `{SCRIPT}`（组合 `--json --paths-only` 模式 / `-Json -PathsOnly`）。解析最少 JSON 有效负载字段：
   - `FEATURE_DIR`
   - `FEATURE_SPEC`
   - （可选地为未来链接流捕获 `IMPL_PLAN`、`TASKS`。）
   - 如果 JSON 解析失败，中止并指示用户重新运行 `/speckit.specify` 或验证功能分支环境。
   - 对于像"I'm Groot"这样的单引号参数，使用转义语法：例如 'I'\''m Groot'（或如果可能的话使用双引号："I'm Groot"）。

2. 加载当前规格说明文件。使用此分类法执行结构化歧义和覆盖范围扫描。对于每个类别，标记状态：清晰/部分/缺失。生成用于优先级排序的内部覆盖范围地图（除非不会提出问题，否则不输出原始地图）。

   功能范围和行为：
   - 核心用户目标和成功标准
   - 明确的范围外声明
   - 用户角色/角色区分

   域和数据模型：
   - 实体、属性、关系
   - 身份和唯一性规则
   - 生命周期/状态转换
   - 数据量/规模假设

   交互和 UX 流：
   - 关键用户旅程/序列
   - 错误/空/加载状态
   - 可访问性或本地化注释

   非功能质量属性：
   - 性能（延迟、吞吐量目标）
   - 可扩展性（水平/垂直、限制）
   - 可靠性和可用性（正常运行时间、恢复期望）
   - 可观测性（日志、指标、追踪信号）
   - 安全和隐私（身份验证/授权、数据保护、威胁假设）
   - 合规/监管约束（如果有）

   集成和外部依赖：
   - 外部服务/API 和失败模式
   - 数据导入/导出格式
   - 协议/版本控制假设

   边界情况和失败处理：
   - 负面场景
   - 速率限制/节流
   - 冲突解决（例如并发编辑）

   约束和权衡：
   - 技术约束（语言、存储、托管）
   - 明确的权衡或拒绝的替代方案

   术语和一致性：
   - 规范术语
   - 避免的同义词/已弃用术语

   完成信号：
   - 验收标准可测试性
   - 可测量的完成定义风格指标

   杂项/占位符：
   - TODO 标记/未解决的决策
   - 缺少量化的模糊形容词（"强大"、"直观"）

   对于每个状态为部分或缺失的类别，添加候选问题机会，除非：
   - 澄清不会实质性改变实现或验证策略
   - 信息最好推迟到规划阶段（内部注释）

3. 生成（内部）最多 5 个候选澄清问题的优先级队列。不要一次全部输出。应用这些约束：
    - 整个会话中最多 10 个总问题。
    - 每个问题必须可以用以下任一方式回答：
       - 短多选选择（2–5 个不同的、互斥的选项），或
       - 一个单词/短语答案（明确约束："用 <=5 字回答"）。
    - 仅包括答案实质性影响架构、数据建模、任务分解、测试设计、UX 行为、操作就绪或合规验证的问题。
    - 确保类别覆盖范围平衡：尝试首先覆盖最高影响的未解决类别；当单个高影响区域（例如安全态势）未解决时，避免提出两个低影响问题。
    - 排除已回答的问题、琐碎的风格偏好或计划级执行细节（除非阻止正确性）。
    - 更喜欢减少下游返工风险或防止错误对齐验收测试的澄清。
    - 如果超过 5 个类别保持未解决，按（影响 * 不确定性）启发式选择前 5 个。

4. 顺序提问循环（交互式）：
    - 一次呈现恰好一个问题。
    - 对于多选问题：
       - **分析所有选项**并根据以下条件确定**最合适的选项**：
          - 项目类型的最佳实践
          - 类似实现中的常见模式
          - 风险降低（安全、性能、可维护性）
          - 与规格说明中可见的任何明确项目目标或约束的对齐
       - **突出显示你的**推荐选项**在顶部，清晰的推理（1-2 句话解释为什么这是最佳选择）。
       - 格式为：`**推荐：**选项 [X] - <reasoning>`
       - 然后将所有选项呈现为 Markdown 表格：

       | 选项 | 描述 |
       |--------|-------------|
       | A | <选项 A 描述> |
       | B | <选项 B 描述> |
       | C | <选项 C 描述>（根据需要添加 D/E，最多 5 个） |
       | 短 | 提供不同的短答案（<=5 字）（仅在自由形式替代合适时包括） |

       - 在表格后，添加：`你可以用选项字母回复（例如"A"）、通过说"是"或"推荐"接受推荐，或提供你自己的短答案。`
    - 对于短答案风格（无有意义的离散选项）：
       - 提供你的**建议答案**基于最佳实践和上下文。
       - 格式为：`**建议：**<your proposed answer> - <brief reasoning>`
       - 然后输出：`格式：短答案（<=5 字）。你可以通过说"是"或"建议"接受建议，或提供你自己的答案。`
    - 用户回答后：
       - 如果用户用"是"、"推荐"或"建议"回复，使用你之前陈述的推荐/建议作为答案。
       - 否则，验证答案映射到一个选项或符合 <=5 字约束。
       - 如果模糊，要求快速消歧（计数仍属于同一问题；不要前进）。
       - 一旦令人满意，在工作内存中记录它（还不要写入磁盘）并移至下一个排队问题。
    - 在以下情况下停止提出进一步问题：
       - 所有关键歧义早期解决（剩余排队项目变得不必要），或
       - 用户发出完成信号（"完成"、"好"、"不再"），或
       - 你达到 5 个提出的问题。
    - 永远不要提前透露未来排队问题。
    - 如果开始时不存在有效问题，立即报告没有关键歧义。

5. 每个接受答案后的集成（增量更新方法）：
    - 维护规格说明的内存表示（在开始时加载一次）加上原始文件内容。
    - 对于此会话中的第一个集成答案：
       - 确保存在 `## 澄清` 部分（如果缺失，在最高级别上下文/概述部分之后创建，根据规格说明模板）。
       - 在其下，为今天创建（如果不存在）`### 会话 YYYY-MM-DD` 子标题。
    - 立即在接受后追加项目符号行：`- Q：<question> → A：<final answer>`。
    - 然后立即将澄清应用于最合适的部分：
       - 功能歧义 → 更新或在功能需求中添加项目符号。
       - 用户交互/演员区分 → 用澄清的角色、约束或场景更新用户故事或演员子部分（如果存在）。
       - 数据形状/实体 → 更新数据模型（添加字段、类型、关系）保留排序；简洁地注释添加的约束。
       - 非功能约束 → 在非功能/质量属性部分中添加/修改可测量的标准（将模糊形容词转换为指标或明确目标）。
       - 边界情况/负面流 → 在边界情况/错误处理下添加新项目符号（或创建此类子部分，如果模板提供占位符）。
       - 术语冲突 → 在规格说明中规范化术语；仅在必要时保留原始，添加 `（以前称为"X"）` 一次。
