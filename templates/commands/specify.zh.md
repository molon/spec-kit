## 用户输入

```text
$ARGUMENTS
```

在继续之前，你**必须**考虑用户输入（如果不为空）。

## 概述

你正在为新功能创建或更新功能规格说明。此工作流通过以下方式引导你：

1. 从用户输入（对话）或现有仓库上下文推导功能需求
2. 生成结构化功能规格说明，包括用户故事、需求和验收标准
3. 创建或更新功能分支和相关目录结构
4. 确保规格说明与项目宪法对齐

遵循以下执行流程：

1. **从用户输入推导功能描述**：
   - 如果用户提供了描述，使用它。
   - 否则，从仓库上下文推断（README、现有规格说明、讨论）。
   - 识别关键需求、用户角色和成功标准。

2. **生成功能编号和分支名称**：
   - 扫描 `specs/` 目录以找到最高现有功能编号（例如 001、002）。
   - 计算下一个编号（例如 003）。
   - 从用户描述生成语义分支名称。
   - 示例：描述"构建聊天系统" → 分支 `003-chat-system`。

3. **创建功能目录结构**：
   - 创建 `specs/[###-feature-name]/` 目录。
   - 复制 `templates/spec-template.md` 到 `specs/[###-feature-name]/spec.md`。

4. **填充规格说明**：
   - 用用户提供的或推断的需求填充 spec.md。
   - 包括：
     - 用户故事（按优先级 P1、P2、P3 排序）
     - 功能需求（FR-001、FR-002 等）
     - 非功能需求（性能、安全、可扩展性）
     - 验收标准
     - 边界情况
   - 对于任何不清楚的内容，使用 `[需要澄清：具体问题]` 标记。

5. **宪法检查**：
   - 读取 `/memory/constitution.md`。
   - 验证规格说明是否与项目原则对齐。
   - 如果存在冲突，标记它们以供后续澄清。

6. **创建或切换分支**：
   - 如果 Git 可用：
     - 创建新分支 `[###-feature-name]`。
     - 提交初始规格说明。
   - 如果 Git 不可用：
     - 仅创建目录结构。
     - 设置 `SPECIFY_FEATURE` 环境变量以供后续命令使用。

7. **生成初始输出**：
   - 输出创建的规格说明的路径。
   - 列出任何标记为 `[需要澄清]` 的项目。
   - 建议后续步骤（例如 `/speckit.clarify` 以细化）。

## 关键规则

- 使用绝对路径。
- 规格说明必须专注于**什么**和**为什么**，而不是**如何**（无技术栈）。
- 用户故事必须独立可测试。
- 所有需求必须是可测量的或可测试的。
- 标记所有歧义以供澄清。
